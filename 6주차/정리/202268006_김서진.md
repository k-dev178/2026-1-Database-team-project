> **이번 주 목표**
> - 개념적 스키마 모델링 사례를 살펴본다.
> - 트랜잭션 모델링의 주요 업무를 설명할 수 있다.
> - 개념적 설계 사례를 살펴본다.

---

## 개념적 스키마 모델링이 뭐예요?

쉽게 말하면, **"우리가 만들려는 시스템에 어떤 정보가 필요할까?"** 를 그림과 표로 정리하는 과정이에요.

예를 들어 **병원 시스템**을 만든다면:
- 의사 정보 필요해!
- 환자 정보도 필요해!
- 검사 기록도 필요해!

이렇게 필요한 것들을 **차근차근 정리**하는 게 개념적 스키마 모델링이에요.

---

## 모델링 8단계 (순서 기억!)

1. **개체 후보 식별** → "누가, 무엇이 있나?" 찾기
2. **개체 후보 검토** → 진짜 개체인지 확인
3. **개체 타입 선정** → 최종 개체 정하기
4. **관계 후보 식별/검토** → 개체 사이의 "행동(동사)" 찾기
5. **관계 유형 및 설명 속성 식별** → 1:N? M:N? 정하기
6. **최종 개체 타입 결정** → 기본키 추가하기
7. **최종 관계 타입 결정** → 관계 이름 다듬기
8. **ER 다이어그램 작성** → 그림으로 그리기

# 사례 1 - 환자 기록 관리 시스템

## 1. 요구사항 (무엇을 관리할까?)

| 번호 | 내용 |
|---|---|
| 1 | 의사는 의사번호, 이름, 진료과목, 휴대폰을 관리 |
| 2 | 환자는 환자번호, 이름, 휴대폰, 주민등록번호를 관리 |
| 3 | 의사가 환자를 진료한 일시, 진단명, 처방을 기록 |
| 4 | 환자의 검사 내역(검사일시, 종류, 결과)을 기록 |
| 5 | 환자 검사를 어떤 의사가 언제 의뢰했는지 기록 |
| 6 | 의사의 담당 진료과목은 1개 이상 |

## 2. 개체 후보 고르기

문장에서 **주어나 목적어**(명사)를 찾아요!

→ 의사, 환자, 검사내역, 검사, 담당진료과목

## 3. 개체 후보 검토

- **검사** = 검사내역과 똑같음 (중복!) → 제외
- **담당진료과목** = 그냥 '진료과목' 속성 하나뿐 → 개체 아님 (다중치 속성 MV로 처리)
- **의사, 환자, 검사내역** → 진짜 개체!

## 4. 관계 찾기 (동사에 주목!)

| 관계 | 연결된 개체 | 유형 | 설명 속성 |
|---|---|---|---|
| **진료하다** | 의사 ↔ 환자 | M:N | 진료일시, 진단명, 처방 |
| **보유하다** (원래 기록하다) | 환자 ↔ 검사내역 | 1:N | - |
| **의뢰하다** | 의사 ↔ 검사내역 | 1:N | 의뢰일시 |

> **'기록하다' → '보유하다'** 로 이름을 바꿨어요. 더 명확하게!

## 5. 최종 개체 타입 + 기본키

| 개체 | 속성 | 기본키 |
|---|---|---|
| 의사 | **의사번호**, 이름, 진료과목(MV), 휴대폰 | 의사번호 |
| 환자 | **환자번호**, 이름, 휴대폰, 주민등록번호 | 환자번호 |
| 검사내역 | **검사번호**, 검사일시, 종류, 결과 | 검사번호 |

> 검사내역은 기본키가 없어서 **'검사번호'** 를 새로 추가했어요!

## 6. ER 다이어그램

```
    [의사] ──(m:n 진료하다)── [환자]
      │                        │
      │ (n 의뢰하다 - 의뢰일시)  │ (1 보유하다 n)
      │                        │
      └────────[검사내역]───────┘
```

# 사례 2 - 쇼핑몰 회원 게시판 관리

## 1. 요구사항

- 회원: 회원번호, 이름, 가입일, 생년월일, 휴대폰, 주소
- 게시판: **상품문의용, 불만접수용** 2개 운영
- 게시판: 번호, 이름
- 회원은 게시판에 **게시글** 등록 가능 (제목, 내용, 작성일시)
- 회원은 게시글에 **댓글** 달 수 있음 (내용, 작성일시)
- 회원은 댓글을 **신고** 가능 (사유, 일시)

## 2. 개체 검토

- 상품문의용게시판, 불만접수용게시판 → '게시판'과 똑같음 (제외)
- 회원, 게시판, 게시글, 댓글 → 진짜 개체

## 3. 관계 찾기 (3진 관계 주의!)

| 관계 | 연결된 개체 | 유형 |
|---|---|---|
| **등록하다** | 회원-게시판-게시글 | **L:M:N** (3진!) |
| **댓글달다** (원래 달다) | 회원-게시글-댓글 | **L:M:N** (3진!) |
| **신고하다** | 회원-댓글 | M:N (사유, 일시) |

> **3진 관계란?** 3개의 개체가 동시에 연결된 관계예요!
> 예) "1명의 회원이 여러 게시판에 여러 게시글을 등록 가능"

## 4. 최종 개체 타입 + 기본키

| 개체 | 속성 | 기본키 |
|---|---|---|
| 회원 | **회원번호**, 이름, 가입일, 생년월일, 휴대폰, 주소 | 회원번호 |
| 게시판 | **번호**, 이름 | 번호 |
| 게시글 | **번호**, 제목, 내용, 작성일시 | 번호 |
| 댓글 | **번호**, 내용, 작성일시 | 번호 |

---

# 3진 관계를 2진 관계로 변환하기

## 왜 변환하나요?

3진 관계는 나중에 논리 모델로 바꿀 때 **너무 복잡**
→ 가능하면 **2진 관계로 쪼개자!**

## 변환 결과

| 번호 | 관계 | 연결 개체 | 유형 |
|---|---|---|---|
| 1 | 게시글_작성하다 | 회원-게시글 | 1:N |
| 2 | 등록하다 | 게시글-게시판 | N:1 |
| 3 | 댓글_작성하다 | 회원-댓글 | 1:N |
| 4 | 댓글달다 | 댓글-게시글 | N:1 |
| 5 | 신고하다 | 회원-댓글 | M:N (사유, 일시) |

> **등록하다**(3진) → 회원이 게시글을 **작성하고**, 게시글을 게시판에 **등록한다** (2진 2개!)
> **댓글달다**(3진) → 회원이 댓글을 **작성하고**, 댓글이 게시글에 **달린다** (2진 2개!)

---

# 댓글 신고 기능이 없는 경우

신고 기능이 사라지면? → **'댓글' 개체도 관계로 바꿀 수 있어요!**

## 바뀐 점

- 댓글 개체 삭제
- 신고하다 관계 삭제
- 회원이 게시글에 바로 댓글 달기 → **댓글달다** (M:N 관계, 속성: 내용, 작성일시)

## 최종 개체 3개만 남음

| 개체 | 속성 | 기본키 |
|---|---|---|
| 회원 | 회원번호, 이름, 가입일, 생년월일, 휴대폰, 주소 | 회원번호 |
| 게시판 | 번호, 이름 | 번호 |
| 게시글 | 번호, 제목, 내용, 작성일시 | 번호 |

## 최종 관계

| 관계 | 연결 개체 | 유형 | 설명 속성 |
|---|---|---|---|
| 작성하다 | 회원-게시글 | 1:N | - |
| 등록하다 | 게시글-게시판 | M:1 | - |
| 댓글달다 | 회원-게시글 | M:N | **내용, 작성일시** |
