# DB 8장 논리적 설계

## 논리적 설계란?

개념적 설계에서 그린 ER 다이어그램을 DBMS가 알아먹을 수 있는 표(릴레이션) 형태로 바꾸는 단계.
쉽게 말하면 도면을 보고 진짜 엑셀 표를 만드는 거.

이 단계에서 하는 일 두 개
- 논리적 스키마 모델링 → ERD를 릴레이션 스키마로 변환하고 정규화
- 트랜잭션 인터페이스 설계 → 사용자가 DB 쓸 때 어떻게 접근할지 정함

변환 순서

    ERD → 릴레이션 스키마(기본형) → 단순화 → 정규화


## 개체는 어떻게 변환하는가?

### 단순 속성만 있는 개체
그냥 속성 그대로 표로. 기본키는 밑줄로 표시.

    사원(사원번호, 이름, 급여)

### 복합 속성을 가진 개체
"주소 = 시 + 동 + 상세주소" 같은 거. 묶음 이름은 버리고 안에 든 것들만 컬럼으로 풀어서 넣음.

    사원(사번, 이름, 시, 동, 상세)

복합 속성을 그냥 통째로 한 컬럼에 넣어버리는 경우도 있긴 한데 보통은 다 쪼개는 게 정석.

### 약한 개체
혼자서는 존재할 수 없는 애들. 부양가족이 대표 예시 (사원이 없으면 부양가족도 의미 없음).

- 강한 개체의 기본키를 외래키로 가져옴
- 그 외래키 + 자기 부분키를 합쳐서 기본키로 씀

예) 부양가족(사원번호(FK), 관계, 이름) → (사원번호 + 관계)가 PK


## 관계는 어떻게 변환하는가?

여기가 사실상 8장의 메인. 1:1 / 1:N / M:N에 따라 처리 방식이 다름.

### 1:1 관계
양쪽 중 한 쪽 골라서 상대 PK를 외래키로 받음. 둘 다 넣어도 되긴 하는데 보통은 참여가 필수인 쪽에 넣는다 (그래야 NULL이 안 생김).

예) 사원-부서 관리 관계
관리하다(사원번호(FK), 부서번호(FK), 임명일자)

### 1:N 관계
N쪽 표에 1쪽 PK를 외래키로 추가. 시험 단골.

예) 부서 1 - 사원 N
사원(사원번호, 이름, 급여, 부서번호(FK))

부서 쪽에 FK를 넣어버리면 한 부서가 여러 사원을 가지니까 한 칸에 여러 값 들어가야 하는 문제 생김. 그래서 N쪽이 정답.

### M:N 관계
새 표를 무조건 만들어야 됨. 이게 제일 중요.

예) 사원 M - 교육과정 N (수강 관계)
수강하다(사원번호(FK), 과정번호(FK), 수강일자, 점수)

두 FK를 합친 게 PK. 근데 같은 사람이 같은 과목을 두 번 듣는 경우엔 이걸로 구분이 안 되니까 수강일자 같은 걸 PK에 추가해야 됨.

### 순환 관계
자기 자신끼리 관계 맺는 거. 사원-관리자 처럼 둘 다 사원인 경우.

- 1:N 순환 → 같은 표 안에 FK 추가. 이름은 다르게 (예: 관리자사원번호)
  사원(사원번호, 이름, 급여, 관리자사원번호(FK))

- M:N 순환 → 별도 표 만들고 두 FK 이름 다르게.
  선수과목(과목번호(FK), 선수과목번호(FK))

순환은 이름 안 바꾸면 충돌 나니까 그게 함정 포인트.

### 3진 관계
개체 3개가 얽힐 때. 셋의 PK를 다 외래키로 가진 새 표를 만들고 셋을 합쳐서 PK.


## 다중치 속성은 어떻게 처리하는가?

한 사람이 여러 개 가질 수 있는 속성 (취미, 자격증 같은 거). 한 칸에 여러 값을 못 넣으니까 별도 표로 빼야 됨.

    취미(사원번호(FK), 취미이름)

사원번호 + 취미이름이 PK.


## 슈퍼-서브 타입은 어떻게 변환하는가?

직원 - 정규직/계약직처럼 상속 관계 있는 애들.

두 가지 방법
1. 슈퍼타입 기준으로 한 표에 다 합치기 → 서브타입끼리 차이 별로 없을 때
2. 서브타입별로 따로 표 만들기 → 차이가 클 때

상황 보고 고름. 근데 보통 차이가 크면 분리하는 게 깔끔함.


## 단순화는 어떻게 하는가?

만든 표를 더 합쳐서 줄일 수 있는 경우가 있음.

- 1:1 관계 단순화 → 한 표에 다른 표 속성을 흡수시키고 나머지 삭제
- 1:N 관계 단순화 → N쪽이 관계에 전부 참여할 때만. 안 그러면 NULL 잔뜩 생김

근데 단순화는 안 해도 되는 거니까 시험에선 보통 기본형까지만 잘 하면 됨.


## 전체 변환 규칙 한눈에 보기

| 경우 | 처리 |
|---|---|
| 단순 속성 | 그대로 옮김 |
| 복합 속성 | 안에 든 거 다 풀어서 컬럼화 |
| 약한 개체 | 강한쪽 PK를 FK로 + 부분키 합쳐서 PK |
| 1:1 | 한쪽에 상대 PK를 FK로 |
| 1:N | N쪽에 1쪽 PK를 FK로 |
| M:N | 새 표 만들고 양쪽 PK를 FK로 |
| 다중치 속성 | 별도 표 |
| 순환 | FK 이름 바꿔서 충돌 방지 |
| 슈퍼-서브 | 통합 or 분리 |


## 꼭 외워야 할 핵심은?
- M:N은 새 표 (이거 안 한 답안 = 0점이라고 보면 됨)
- 약한 개체 PK는 강한쪽 FK + 부분키
- 다중치는 한 칸에 못 넣음 → 새 표
- 순환 관계 FK는 이름 다르게
- PK 밑줄, FK는 옆에 (FK)


## 알아둬야 할 용어는?

- 릴레이션: 표 자체
- 튜플: 행 하나
- 속성: 컬럼
- 도메인: 그 속성이 가질 수 있는 값의 범위
- 스키마: 표의 구조 (헤더)
- 인스턴스: 실제 들어있는 데이터
- 기본키(PK): 행을 유일하게 구분
- 외래키(FK): 다른 표 PK 참조
