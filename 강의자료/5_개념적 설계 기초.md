# 개체 식별 방법
## 개체 후보 식별
- 데이터 요구 분석 명세서에서 주로 주어나 목적어로 표현된 것이 개체 타입 후보가 될 수 있다.

## 개체 후보 검토
- 각 개체 후보의 실제 데이터 수와 대표 속성을 파악하고, 동음이의어나 이음도의어 등도 검토한다. 
- 또한 동사로 표현되었는데(또한 동사화 할 수 있는데) 개체로 잘못 추출된 것이 있는지 검토하고, 필요한 경우 개체 이름을 변경할 수 있다.

## 개체 타입 선정
- 실제 데이터, 즉 개체 인스턴스가 2개 이상 존재하고 2개 이상의 속성을 지닌 개체 후보를 개체타입으로 선정한다. 
- 단, 동일한 의미를 지닌 개체가 있으면 제외해야 한다. 
- 개체 후보의 속성이 하나밖에 없다면 그 개체 후보는 다른 개체 타입의 속성으로 표현하는 것이 적절하다.
- 만약 개체 인스턴스의 수가 1개이고 앞으로 추가될 가능성이 없다면 그 개체는 굳이 DB에 표현할 필요가 없으므로 개체 타입으로 선정하지 않아야 한다.
- 또한 추후 관계 식별 단계에서 관계로 표현하는 것이 더 적합한 개체가 있으면 이 개체 역시 개체 타입에서 제외해야 한다.

# 관계 식별 시 유의 사항
- 관계는 개체 간의 상호 연관성을 표현하는 것으로, 개체와 관련된 업무 수행 규칙에 해당한다. 따라서 데이터 요구 분석 명세서에서 주로 동사 또는 동사화할 수 있는 형태로 표현되는 경우가 많다.
- 업무를 충분히 파악한 다음 전체 업무를 고려해서 넓은 시각으로 분석해야 한다.
- 업무 규칙이 변경됨에 따라 관계도 변경될 수 있음을 염두에 둔다.
- 특히 초보자가 개체와 관계를 명확히 구분하기는 쉽지 않으므로, 식별된 개체 가운데 '관계'로 표현하는 것이 적합한 단어가 있는지 검토한다.
- 관계는 기본적으로 관계에 포함된 양쪽 개체의 기본키를 속성으로 갖는다. 관계의 속성을 파악할 때는 관계를 설명하기 위해 추가로 필요한 속성을 파악하는 데 집중한다.

# 속성 식별 방법
속성(attribute)은 개체나 관계의 특성을 나타내는 요소로, 이름을 가진 정보의 가장 작은 논리적 단위다. 속성은 더 이상 분리할 수 없는 데이터 값을 저장하는 곳으로, 일종의 데이터 저장소라 할 수 있다.

속성을 식별하는 방법은 다음과 같다.

- 데이터 요구 분석 명세서에서 개체를 설명하는 명사를 개체의 속성으로 식별한다.
- 데이터 요구 분석 명세서에서 관계를 설명하는 명사를 관계의 속성으로 식별한다.
- 데이터 요구 분석 명세서에서 개체의 기본키 속성을 식별할 수 없을 때는 기본키 역할을 할 속성을 추가한다.
- 데이터 요구 분석 명세서에는 없지만 개체나 관계의 특성을 설명하는 데 필요한 속성이 있다면 이 속성을 추가로 식별한다.

# 트랜잭션 모델링의 주요 업무
DB에서 수행될 작업(트랜잭션)을 분석·정리하는 업무입니다.

주요 업무

1. **트랜잭션 식별**
   - 트랜잭션 요구 분석 명세서를 바탕으로 시스템에서 수행되어야 할 트랜잭션들을 뽑아낸다.
   - 예: 회원가입, 주문등록, 재고조회, 매출집계 등.

2. **트랜잭션 입·출력 분석**
   - 각 트랜잭션의 입력 데이터(파라미터), 출력 데이터(결과), 처리 흐름을 분석한다.
   - 어떤 개체/속성을 읽고(read) 어떤 개체/속성을 쓰는지(write) 파악.

3. **트랜잭션 유형 분류**
   - 검색(read-only), 갱신(insert/update/delete) 등으로 구분.
   - 개념적 스키마와의 정합성 확인용.

4. **트랜잭션 빈도·우선순위 분석**
   - 얼마나 자주 발생하는지, 응답시간 요구가 까다로운지 파악.
   - → 이후 물리적 설계(인덱스 설계 등)의 근거가 됨.

5. **트랜잭션 명세서 작성**
   - 트랜잭션 이름, 입출력, 처리 로직, 빈도, 우선순위 등을 표준 양식으로 정리.

## 왜 같이 하나?
개념적 스키마(데이터 구조)만 잘 만들어도 부족하다.
실제로 그 구조 위에서 어떤 작업이 돌아갈지 미리 분석해 둬야
→ 누락된 속성 발견, 비효율 구조 사전 차단, 이후 물리적 설계의 기반이 된다.
